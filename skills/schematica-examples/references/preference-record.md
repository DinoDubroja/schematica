# Visual preference record

Use this format when saving or refining an approved general schematic preference. Its page serves both humans and agents; keep the rule in one authoritative place.

## Resolve scope before saving

Check the accepted index and pending suggestions in `preferences/GENERAL.md`. Reuse a matching preference and stable ID. Decide whether the lesson is general, style-specific, or local; keep style exceptions in the selected style guide and local feedback with the example. Never silently promote a candidate into an accepted default.

An explicit instruction to adopt a clearly scoped preference is sufficient approval for its agreed page, illustrative assets, index links, and checks. Do not ask the user to manage filenames or approve each routine file operation. Record tentative observations in the authorized context/inactive queue without treating them as rules. A new publication of full source examples or unrelated supplied material must remain within the actual save scope.

## One page per preference

Use `preferences/<descriptive-topic>/README.md` for the authoritative page. Include:

- **Title, stable ID, status, and decision date.** Accepted, proposed, deferred, or rejected must be unmistakable; only accepted rules are active defaults.
- **Visible example or comparison.** Put the image near the top. When two images help, show them side by side at a matched scale with precise before/after or preferred/avoid captions. Explain the specific feature being judged; do not label an entire circuit bad because one detail was corrected.
- **Rule and scope.** Use concise, actionable wording. State when it applies and relevant exclusions. Link the common precedence guide; do not duplicate it.
- **Reason, evidence, and provenance.** Link supporting example records/corrections and record what the user actually approved. Distinguish direct feedback from inference and a historical render from a new focused reconstruction. Rule approval and the review status of new illustration assets are separate facts.
- **Files and navigation.** Link editable source when available, full-size previews, the preference gallery, and the agent index. Omit missing files rather than create placeholders.

Keep each image tied to a clear lesson. Several examples may support one rule, and one original circuit may support several rules; link back to the source instead of copying the whole circuit into every preference folder.

## Comparison assets

Use the user's supplied images when their preservation is authorized, selected generated revisions, or a focused reconstruction when useful. Never invent an earlier image or imply that a reconstruction is a historical screenshot. Preserve a useful before image when approved instead of overwriting it with the corrected result. Keep unrelated circuit details identical where possible so the comparison isolates the lesson.

For generated drawings, keep editable source and a matching rendered preview. Follow the [presentation procedure](../../../scripts/PRESENTATION.md) for transparent, theme-appropriate README/chat assets and ordinary file links. If separate light/dark SVGs are needed for the host renderer, derive them from the same geometry. Verify contrast, transparency, hollow interiors, and labels in both themes. Derivatives are generated assets, not independent sources to edit manually. Do not impose exact symbol dimensions or typography as general rules merely because they appear in an illustration.

## Index and gallery

- `preferences/GENERAL.md` owns precedence and the agent selection index, plus clearly inactive pending/deferred/rejected suggestions. Link each accepted rule to its page; do not repeat its normative text in the index.
- `preferences/README.md` is the human gallery. Show thumbnails and short titles linking to accepted pages with actual visuals. Keep unresolved suggestions visibly separate from the accepted bank.
- Link the gallery from the main project README. Keep the route from `AGENTS.md` through the index to applicable rules and visuals explicit.
- When a candidate is accepted, move its authoritative rule to the page and retain a short decision reference. Do not leave conflicting active copies behind. Retire or supersede earlier wording explicitly when a rule changes.

## Finish

Read the rule and evidence back, inspect every supplied/generated comparison, check links and stable IDs, and verify source/preview agreement. Check that the documented preference does not change electrical meaning, invent a style override, or exceed the user's approval. Preserve concurrent work and follow the repository's commit/push instructions for the scoped save.
